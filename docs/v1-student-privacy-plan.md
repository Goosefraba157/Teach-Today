# V1 Student Privacy Plan

## Objective

Keep Teach Today useful and recognizable for one teacher while preventing student records from being exposed through public source code, public URLs, permissive cloud rules, shared displays, or exports.

This is a privacy-by-design engineering plan aligned with FERPA-oriented safeguards. It is not a legal certification; district policy and approval still govern use of student education records.

## Teacher Experience

- Teacher display name: first name plus last initial, such as `Sofia C.`
- Optional teacher-only nickname
- Context shown when helpful: school year, grade, and active group
- Student/projector display: first name or nickname only
- Cross-year profile: one recognizable student timeline organized by school year

## Identity Model

Each student receives a random permanent `studentId` generated by the app. Names, school IDs, group names, or dates must not be used to construct this identifier.

```text
Student
  studentId: random permanent ID
  displayName: first name + last initial
  teacherLabel: optional teacher-only label

Enrollment
  enrollmentId: random ID
  studentId: permanent student reference
  schoolYearId: year reference
  groupId: active group for that year
  grade: optional
  status: active | archived

Record
  studentId: permanent student reference
  schoolYearId: year when evidence was collected
  groupIdAtTime: historical group reference
  occurredAt: timestamp
```

## Identifier Handling

- Do not put district/student ID numbers in Git, public JavaScript, URLs, filenames, analytics, or browser-visible logs.
- Use district/student IDs only inside a private roster-import matching step.
- Prefer storing a keyed, non-reversible matching value rather than the raw district ID after matching.
- Never derive the matching value with an unsalted public hash; predictable school IDs can be guessed.
- Keep the matching key outside public source code and separate from ordinary records.
- Everyday records reference only the random `studentId`.

## Storage Boundaries

### Public GitHub Pages

- Application code and generic demonstration data only
- No real names, schools, groups, IDs, notes, results, recordings, or roster files

### Local Browser

- Local-first working copy for the signed-in teacher
- No sensitive values in URLs
- Clear warning that browser storage is readable by anyone using the same unlocked browser profile
- Managed device, screen lock, and a dedicated browser profile recommended

### Firebase

- Firebase Authentication required
- Teacher data stored below the authenticated teacher UID
- Security Rules require `request.auth.uid` to match the owner UID/path
- Student-facing access limited to one student's minimum necessary fields and activities
- Deny collection-wide listing of student codes
- App Check considered as an additional abuse control, not a substitute for Authentication and Security Rules

## Migration Order

1. Export and preserve the current V1 state.
2. Add schema version and school-year metadata without changing UI behavior.
3. Assign random permanent IDs to existing roster entries and backfill records.
4. Label existing groups, plans, and records with the prior school year.
5. Replace public real roster defaults with generic demonstration data.
6. Add authenticated/private roster loading.
7. Add local CSV roster import and returning-student matching.
8. Add archive and school-year selection UI.
9. Tighten Firestore and Storage rules, test authorized and unauthorized cases, then deploy rules.
10. Remove student data artifacts from the current public site and evaluate Git-history cleanup separately.

## Non-Destructive Guarantees

- Archiving changes visibility and enrollment status; it never deletes records.
- Migration retains original group and display-name fields on historical records until verification is complete.
- A migration receipt records counts before and after each transformation.
- Existing V1 lesson and presentation routes remain unchanged during the privacy foundation work.
- Each stage is committed and tested separately so rollback is possible.

## Current Audit Findings

- Real roster defaults and school names are embedded in `app.js` and therefore exposed by public GitHub Pages.
- The primary local/Firebase backup payload already stores the full V1 state under a teacher-specific authenticated path.
- Some Firestore collections currently grant broad access to any Google-authenticated user through the `isTeacher()` helper; owner-scoped rules are required.
- Student matching still falls back to group plus normalized name, which cannot reliably preserve identity across school years.
- Some local storage keys are keyed by student ID, while older records and groups still use names. Migration must support both during transition.

## Completion Criteria

- No real roster appears in publicly served source or default data.
- An unauthenticated user cannot read any roster, lesson record, activity, code, or recording.
- One authenticated teacher cannot read another teacher's data.
- Student access cannot list or read another student's records.
- Returning students retain one permanent identity across multiple school years.
- Teacher views remain recognizable using first name plus last initial and context.
- Prior-year groups can be archived and restored without data loss.
